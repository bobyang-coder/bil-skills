# 设计文档（团队模板）

按团队固定模板生成、改写或评审设计文档。结构固定：**文档头 → 需求 → 设计 → 排期 → 提测 → 上线 → 风险与待确认 → 其他**。正文使用中文；代码、类名、字段名、SQL、API 路径保留英文。

## 工作流程

1. 若用户已给出完整需求，直接进入第 2 步；若信息不足，先一次性提出 3 个关键问题（不要逐个追问）：
   - **背景与目标**：这个功能/系统要解决什么问题？
   - **技术栈与约束**：语言/框架/版本？依赖哪些现有系统？
   - **范围与交付**：一期范围？明确不做的事？（新项目还是存量系统改造）
2. 按下方【模板】输出：先写文档头，再输出 `[TOC]`，再按 一 → 七 章顺序填写。**每章按其子标题清单生成 `##`/`###` 子标题**，不得退回列表式。
3. 每章必须有实质内容；信息不足的章节写当前已知信息，并把待确认项列入第六章【风险与待确认】，不得写"待补充"。
4. 排期表中的时长标注"（估算）"，数值不得编造。
5. 用户要求"评审"时，按模板逐章核对并输出问题清单，而不是重写全文。

## 模板

### 文档头

| 项目名 | （需求名称） | 作者 | （编写人） |
| --- | --- | --- | --- |
| 日期 | （编写日期） | 版本号 | v1.0 |
| 评审人 | 待定 | 评审结论 | 待评审 |

[TOC]

# 一、需求

> 固定生成以下子标题：需求地址 / 需求背景 / 需求分析 / 非功能需求 / 验收标准

## 需求地址

需求单 / JIRA 链接或编号；无则写"无"。

## 需求背景

业务现状与痛点，为什么现在要做。

## 需求分析

功能点列表（编号 FR-1…），每项含优先级（P0/P1/P2）。

## 非功能需求

性能指标（QPS / RT）、可用性、安全要求、数据量预估。

## 验收标准/成功指标

目标可量化，说明上线后如何判定成功。

# 二、设计

## 工程设计

> 固定生成以下子标题：系统架构 / 模块划分与职责 / 项目结构 / 兼容性与数据迁移 / 依赖与影响面。【新项目三项必须有，存量系统改造可只写受影响部分】

### 系统架构

架构图（Mermaid 或 ASCII）。

### 模块划分与职责

模块/职责/依赖方向。

### 项目结构

包结构与分层关系。

### 兼容性与数据迁移

老接口兼容、存量数据迁移、双写等。【一般存量系统改造才有】

### 依赖与影响面

上下游系统、关联方。

## 业务设计

> 固定生成以下子标题：业务能力 / 业务时序图、逻辑图

### 业务能力

要实现哪些功能，最好是表格形式。

### 业务时序图、逻辑图

画图主要用 Mermaid 格式，也可以用别的格式，能在 markdown 中预览即可。

## 模型设计

> 这里可以按具体内容增加相应子标题：【无此类要点可不写】。模型关系为固定子标题，其余（表结构 DDL / 状态机 / 关键点说明 / 数据量与容量评估）按需生成。

### 模型关系

ER 图或关系说明。

### 表结构 DDL

完整可执行，字段带注释、索引、主键；如果 SQL 能讲明白，最好用 SQL。

### 状态机

如实体有状态流转，列出状态与迁移条件，最好用图的形式展示。

### 关键点说明

### 数据量与容量评估

存量、日增量、峰值、增长策略。

## 技术选型

> 固定生成子标题：选型对比

### 选型对比

必须给出对比表和最终选择原因，不得只写结论。

## 技术实现

> 按关键技术点各生成一个子标题（如 `### 分布式锁`、`### 分布式事务`），无此类要点可不写

每个关键技术点：方案对比表（方案/优点/缺点/结论）+ 最终选择原因；对比表格式视情况自行扩展。核心代码示例按需写。

## 接口设计

> 若有接口文档地址（如 swagger），直接列表格即可，不用过多说明；否则固定生成：接口清单 / 关键接口详情 / 错误码表

### 接口清单

表格列出 方法/路径/说明/鉴权。

### 关键接口详情

请求示例 JSON、响应示例 JSON（成功与失败）。按需写，不必每个接口都给。

### 错误码表

按需写。

# 七、其他

> 补充说明、未尽事宜

## 输出规则

1. 结构顺序固定：文档头 → [TOC] → 一、需求 → 二、设计 → 三、排期 → 四、提测 → 五、上线 → 六、风险与待确认 → 七、其他，不得省略、合并或重排。设计章子节顺序固定：工程设计 → 业务设计 → 模型设计 → 技术选型 → 技术实现 → 接口设计。
2. 章节标题使用模板原文（含中文编号"一、二、…"）：章用 `#`，章内子标题用 `##`，设计章子节下的要点用 `###`。
3. **子标题规则**：标注"固定生成"的章节按子标题清单生成子标题，某子标题确无内容时省略并在该章末尾注明"本版本不涉及：xxx"；标注"按具体内容增加"的章节（模型设计/技术选型/技术实现）按需生成子标题，无此类要点可不写，无需注明。不得退回列表式要点。
4. 文档头必须完整；信息不确定时写"待定"，不能留空。
5. 可酌情增加子层级，但层级最好不要超过 6 级。
6. 正文中文；代码、类名、字段名、SQL、API 路径、错误码保留英文。
7. 排期/上线表格保留模板原表头，行可增删。
8. **技术选型与技术实现章节必须给出对比表和最终选择原因**，不得只写结论。
9. 模型设计必须给出表结构（字段含类型/约束/说明）与数据量/容量评估；无 DDL 时说明原因。
10. 需求章必须包含验收标准；上线章必须包含回滚方案、监控与告警、灰度策略。
11. 新项目与存量系统改造写法不同：新项目工程设计三项（架构/模块/结构）必须有；存量改造可只写受影响部分，但必须覆盖兼容性与数据迁移。
12. 拿不准的决策写入第六章，不得编造。

# 一、需求

## 需求地址

无（待补充需求单链接）。

## 需求背景

运营与财务需要定期按条件筛选订单并导出 Excel 进行分析与对账，目前依赖人工导出，效率低。

## 需求分析

| 编号 | 功能点 | 优先级 |
| --- | --- | --- |
| FR-1 | 按条件筛选订单并导出 | P0 |

## 非功能需求

导出接口响应时间 ≤ 30s（估算）；不影响订单主链路。

## 验收标准/成功指标

5 万行导出耗时 ≤ 30s（P99，估算）；导出接口错误率 < 0.1%。

## Do NOT

- 不要省略、合并或重排章节（一 → 七），也不要省略文档头。
- **不要退回列表式要点**——每章必须生成子标题结构。
- 不要生成空子标题（无内容时省略并在章末注明"本版本不涉及"）。
- 不要只输出目录框架而没有实质内容。
- 不要编造技术选型对比、方案对比、工时或表结构；不确定的写入第六章。
- 技术实现与技术选型章不要只写结论、不写对比。
- 不要替用户决定架构（如"引入消息队列"），应列为待确认问题。
- 需求章不要漏掉验收标准；上线章不要漏掉回滚方案、监控告警、灰度策略。
- 模型设计不要漏掉数据量/容量评估。
